# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"โรงเตี๊ยม" (Rongtiam): a realtime multiplayer virtual tabletop (in the spirit of Owlbear Rodeo) with a Thai UI. Vite + TypeScript + Svelte 5 frontend (static, deployed to Vercel) on Supabase (Postgres + RLS, Realtime broadcast/presence, Storage, anonymous auth). Keep user-facing strings in Thai. `legacy/dnd-table.html` is the original single-file app; it is the reference the table code was ported from — don't edit it.

The roadmap lives in the approved plan; phases 1 (foundation), 2 (fog, hidden items, Sync View), 3 (3D dice), 4 (ruleset plugins, sheets, HP/conditions, initiative) and 5a (the level-1 D&D 2024 character builder) are what exists now. Phase 5 is split in three: 5a builder (done), 5b level-up, 5c homebrew; their specs and plans are in `docs/superpowers/`.

## Commands

```bash
npm run dev            # Vite dev server; /local is an offline single-player table (dev only, no Supabase needed)
npm test               # Vitest: unit tests (src/**/*.test.ts) + database tests (tests/db) in PGlite
npx vitest run src/sync/state.test.ts   # one file;  add  -t "name"  for one test
npm run test:db        # only the SQL/RLS tests
npm run check          # svelte-check + tsc
npm run build
npm run e2e            # Playwright GM+player flows against the real Supabase dev project (skips without .env.local); one spec: npx playwright test tests/e2e/sheets.spec.ts
npx playwright test tests/e2e/builder.spec.ts   # the character builder at 375×812 on /local; needs no Supabase
npm run db:push        # supabase db push (after `supabase link --project-ref <ref>`)
npm run db:types       # regenerate src/supa/types.gen.ts from the linked project
node scripts/srd/fetch.ts && node scripts/srd/build.ts   # refresh the D&D SRD data (see Rulesets)
```

Supabase config comes from `.env.local` (see `.env.example`). There is no Docker here: develop against a cloud dev project and change the schema only through new files in `supabase/migrations/` (never dashboard edits). The e2e specs need every migration applied to the dev project first. If `db push` is refused (403 at "Initialising login role"), run the migration file through the Supabase SQL tool and insert the matching row into `supabase_migrations.schema_migrations`, so a later `db push` sees it as applied.

## Architecture

**Server is the permission boundary.** `supabase/migrations/` holds everything:
- Tables `rooms` (`ruleset_id` = the room's game system), `room_members` (role gm|player, status pending|approved|banned), `items` (kind map|char|sticker|fog, `props` flat jsonb, `meta` jsonb namespaced per ruleset, `z`, `locked`, `hidden`), `assets`, `roll_log`; `room_secrets` (GM key hash, no policies) and `room_clock` (per-room `seq`). Phase 4: `characters` (owner, ruleset, `visibility` party|gm, `data` jsonb owned by the ruleset), `room_content` (GM-authored: the custom template, homebrew; kind/key) and `initiative_entries` (turn/round live in `rooms.settings.initiative`).
- RLS: characters are edited by their owner (party only) or a GM; `visibility='gm'` (secret NPCs) rows and hidden initiative entries reach only GMs (gm topic), exactly like hidden items; players put only their own characters into initiative; room_content is GM-written. Sheets are edited field by field through `character_patch(id, ops)` (security invoker, `{path, value}` ops, null removes, parents created).
- RLS: maps/fog/lock/hide are GM-only; players add/move/delete unlocked, visible chars and stickers. Membership changes go through the security-definer RPCs `create_room`, `request_join`, `claim_gm`; `members_guard` blocks non-GMs from changing role/status on direct updates (it checks `current_user = 'authenticated'`, so trusted RPCs pass).
- All item writes go through `apply_ops(room, ops)` (security **invoker**, so RLS applies; one transaction per batch; patch props merge with `null` deleting a key; meta merges per namespace; raises 42501 when an update matches nothing; returns rows actually written/deleted).
- BEFORE triggers stamp `rev = private.tick(room)` (monotonic per room); AFTER triggers broadcast committed rows with `realtime.send` to `room:<id>:db` (members) or `room:<id>:gm` (GMs). **Hidden items are only ever sent on the gm topic**; hiding a visible item also sends `{op:'del', reason:'hidden'}` on db. `room:<id>:live` is the only client-writable topic (ephemeral drags/pings + presence).
- `room_snapshot(room)` returns everything the caller may see in one statement.
- `tests/db/` runs the real migrations in PGlite on top of `tests/db/supabase-stubs.sql` (fake `auth`, `realtime`, `storage`, roles). Add a test there for every policy/RPC change; they run in `npm test`.

**Client sync** (`src/sync/`):
- `state.ts` `RoomState`: confirmed rows + this client's pending (optimistic) layer. Events older than the stored `rev` are ignored; deletes are tombstoned; events that arrive while a snapshot loads are buffered and replayed if `rev > snapshot.seq`. `get(id)` = confirmed ⊕ pending.
- `opqueue.ts`: coalesces patches per item (delay param: sliders ~150 ms, typing ~400 ms, drag commit 0), sends one batch at a time, retries network errors, rolls back on permanent errors (42501 etc.).
- `ephemeral.ts`: throttled live messages; rate `budgetHz(online)` keeps the project under Supabase's free 100 msg/s (deliveries count).
- `room.svelte.ts` `RoomStore`: wires backend + state + queue + bus + `AssetCache`; exposes `*Version` rune counters that Svelte `$derived` blocks read (`void store.itemsVersion`). Resyncs on channel rejoin, `online`, and tab visible after >30 s.
- `backend.ts` interface; `src/supa/backend.ts` (Supabase) and `local.ts` (in-memory, dev `/local`).

**Table** (`src/table/`): `Stage.ts` is the imperative port of the legacy IIFE (view transform with `--inv`, pointer/pinch/drag/rotate, map snapping via `lib/geometry.ts`). It renders from `store.item(id)` plus its own drag `overrides` and eased remote `previews`; a drag broadcasts throttled previews and commits **one** patch on pointerup (with `z = topZ` to lift non-maps). `canEdit`/`canSelect` mirror RLS so the UI never offers refused actions. Stacking is by `z` within each layer group (maps, items, fog; `store.topZ`). Sync View: the GM sends `view` `{cx,cy,w,h}` on `live`; players fit that world area (only accepted from members whose role is gm). `actions.ts` adds maps/chars/stickers: images go through `images.ts` (resize/re-encode, file named `<sha256>.<ext>`), upload once to the private `room-assets/<room>/` bucket, are cached in IndexedDB, and items reference the file name in `props.img`.

**Fog** (`src/fog/`): each fog item is one shape, `props {mode: 'add'|'cut', geom: int rings [[x0,y0,x1,y1,…],…]}`. `geometry.ts` (Clipper2 via `clipper2-ts`) folds shapes in `z` order into the visible fog (`computeFog`), builds rect/polygon/brush rings (brush: RDP → round offset → simplify, ≤ 4000 points; compacted ≤ 12 000) and hit-tests. `FogLayer` owns the fog layer above the items: `FogCanvas` paints it on a screen-sized canvas placed in world space (fog clipped to the view → feathered with the canvas shadow trick → filled with two drifting, opaque cloud textures from `clouds.ts`; ~15 fps drift, still under `prefers-reduced-motion`; GM at 45 % unless "ดูแบบผู้เล่น"), with SVG overlays for previews and the selected shape; `FogTool` handles GM drawing, picking and the local undo stack — deleted ids can never return (tombstones), so undo restores shapes under fresh ids. Fog is visual only: items under it are still sent to players; secrecy is `hidden`.

**Dice** (`src/dice/`): `model.ts` parses expressions (`2d20kh1+1d4+3`, `d100`; ≤ 24 physical dice), expands them into physical dice (a d100 is a tens + a units d10; 00 + 0 = 100) and evaluates landed faces into the `roll_log` result. `geom.ts` builds the polyhedra by hand (d10 = pentagonal trapezohedron), assigns face values (opposites sum like real dice) and reads the top face via per-value locators (d4 reads its top corner). The **roller's browser decides**: `physics.ts` (Rapier, lazily imported, never prefetched on touch devices) simulates the whole throw up front (≤ 960 steps of 1/120 s, keyframes at 30 Hz, quantised ints; leaning dice are eased flat), `director.ts` sends `roll` on `live` with the keyframes, writes the `roll_log` row (client-chosen id = the replay's id; the official result), and replays; others replay from the keyframes with `render.ts` (three.js, lazy) and the on-table result waits until the dice land (`after(id)`). A GM secret roll sends only `{secret:true}` on live (players see "GM ทอยลับ"); its row only goes on the gm topic. Fallbacks: reduced motion → final pose at once; no WebGL → 2D result only; Rapier can't load in 10 s → crypto `rand` with `engine:'crypto'`. `protocol.ts` validates incoming `roll` messages (sender must be an approved member). `physics-consts.ts` keeps Rapier out of the main bundle. Fairness check: `DICE_FAIR=1 npx vitest run src/dice/physics.test.ts`.

**Rulesets** (`src/rulesets/`): the table knows no game system. `core/types.ts` `RulesetModule` (newCharacter, parse, rolls, conditions, bars, applyHp, initiative, lazy `Sheet`), `core/formula.ts` (Pratt parser, no eval: + - * /, floor/ceil/min/max/abs/mod, `@field` refs with cycle detection, dice → a dice expression for the 3D roller), `registry.ts` (lazy modules), `host.svelte.ts` `RulesetHost` (loads modules, room content as context, token status for the Stage). `dnd2024/`: zod `model.ts` (choices + play state only), pure `derive.ts` (mods, PB, saves, skills, AC incl. Unarmored Defense, HP, speed, attacks, spell DC/slots/pact), `rules.ts` (roll buttons, temp-HP-first damage, conditions), `Sheet.svelte`; SRD 5.2 data from Open5e: `node scripts/srd/fetch.ts` → `data/srd/raw/<date>/` (committed) → `node scripts/srd/build.ts` → `data/srd.json` (zod-validated; known Open5e errors fixed in a reported `CORRECTIONS` list; attribution in `LICENSE-SRD.md` and `/credits`). `custom/`: the GM designs the system in `TemplateEditor.svelte` (sections, number/text/formula/choice fields, catalogs of their own content such as careers or weapons, per-character lists with per-row rolls, roll buttons, token bars, conditions, initiative), stored as room_content `template/main`; `model.ts` derives it with the formula engine (`@choice.column`, `@row.column`). Sheets (`src/sheets/`): `SheetPanel` docks over the table (dice roll over it), `SheetsSection` lists/creates/imports, `transfer.ts` is the `tabletop-character` file format, `InitiativeTracker` + pure `initiative.ts`. Skills: D&D rooms get GM-defined skills (room_content `homebrew/skills` `{skills, allowPlayerSkills}`, edited in `dnd2024/RoomSkillsEditor.svelte`, derived by `roomSkills.ts`) and players' personal `customSkills` on the sheet; custom templates carry `skills {roll, allowPlayerSkills, list}` with one roll formula over `@stat`/`@rank` and per-character `skillRanks`/`customSkills`. With `allowPlayerSkills` off only a GM can add personal skills. Tokens bind to sheets via `meta.core.characterId` (or GM-only quick NPC HP `meta.core.hp`, public with `hpPublic`); `Stage.renderStatus` draws bars and condition icons.

Phase 5a (D&D character builder): `scripts/srd/build.ts` also reads each class's Core Traits table (`feature_type === 'CORE_TRAITS_TABLE'`) through `data/coreTraits.ts` into `skillChoice`, `training`, `tools`, `equipmentOptions` (and the Warlock's `invocations`, background `tools`/`equipmentOptions`), repairing words the PDF split ("Ar mor") and failing the build when a class's skills or equipment can't be read. `dnd2024/overlay/` is hand-written and cross-checked against srd.json by its tests: `classes.ts` lists the decisions a player makes per class level (subclass, ASI, expertise, Weapon Mastery, orders, invocations, metamagic; counts that sit in the class table are read from it), `species.ts` the species choices, `languages.ts` the standard languages. `builder/`: a `Draft` (zod, saved per room in localStorage by `persist.ts`) is checked by pure `validate()` (issues tagged by wizard step) and turned into a `D2024` by pure `build()` (effects land in the sheet's own fields, the whole draft is kept in `choices.build`, feature effects beyond `derive()` are text only); `Builder.svelte` + `steps/*` is the nine-step wizard, loaded through `RulesetModule.Builder` and hosted by `sheets/BuilderPanel.svelte` (mounted in `Table.svelte`, `ui.builderOpen`). The ability-score roll is one `4d6kh3` ×6 throw read with `scoresFromRoll`, saved to the draft from `DiceDirector.roll`'s `onDecided` before the dice land (a reload mid-roll cannot buy a re-roll). "สร้างตัวละคร" opens the builder (it waits for the ruleset module first), "สร้างชีทเปล่า" keeps the blank sheet. `fixtures.ts` `autoDraft()` makes a valid draft for any class × background × species (used by the matrix test).

**Routes**: `/` create/join, `/credits` (SRD attribution), `/r/<slug>` (anonymous sign-in → optional `#gm=<key>` claim, fragment stripped → join form / waiting poll / table), `/local` (dev). Per-viewer prefs (view, snap, profile, recent rooms, GM keys) live in localStorage.

## Conventions

- CSS tokens in `src/app.css` `:root`, redefined for dark mode under `prefers-color-scheme` (guarded by `:root:not([data-theme="light"])`) and `:root[data-theme="dark"]` — add new colours in all three. The viewer's choice (system/light/dark) is `lib/theme.ts` → `data-theme` on `<html>`; each theme also sets `color-scheme` (native controls follow it) and `select option` has an explicit themed background, so don't restyle those per component.
- Destructive buttons use `ui/TwoStepButton.svelte`. Keyboard shortcuts live in `Stage.onKey` (Tab reaches every selectable item and focusing selects it; arrows nudge the selection, Shift = one grid cell; V/1, 2, 3, 4 = fog for GMs, Space (only when focus is on the table, so buttons still activate), F, H, T, Q/E, +/-, Esc, Delete; with the fog tool: R/P/B/S shape, X add↔cut, Alt held = invert, Enter/Esc/Backspace for polygons, Ctrl+Z); update tooltips and Thai help text with them.
- Real `<button>`s with `aria-pressed`/`aria-label`; respect `prefers-reduced-motion`. The side tabs follow the ARIA tabs pattern (one tab stop, arrows/Home/End); toasts are announced from a persistent `role=status` region. Text in the accent hue uses `--accent-text`, destructive actions and errors use `--danger`, pressed segments use `--teal-solid`/`--teal-ink`.
- Rolls use the physics simulation, seeded from `lib/rand.ts` (`crypto`; `randFloat`, and `rand` with rejection sampling for the fallback).
- Anything laid over the table that must not feed the Stage's pointer/wheel/keyboard handlers (sheet, tracker, editors) carries the `overlay-ui` class; the dice canvas and tags stay above the sheet in z-order. A ruleset's `Sheet` component is loaded once into `$state` and keyed by character id, never inside `{#await}`, or it remounts on every data change and loses focus.
- An async handler that outlives its UI (a roll that finishes after the sheet closed) must capture the ids/data it needs before the first `await`; reading `$derived` state afterwards can find it gone.
